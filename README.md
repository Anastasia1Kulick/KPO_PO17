## Порядок работы

1. Делаем **форк** этого репозитория к себе в аккаунт.
2. Выполняем лабораторную работу.
3. Коммитим отчёт, код и **свои тесты** в свою ветку форка.
4. Делаем **Pull Request** в `main` этого репозитория.
5. Дожидаемся автоматических проверок (см. ниже) и результатов проверки преподавателем.

### Команды git

1. `git clone <url-адрес вашего форка>` — клонирование в локальную папку
2. `git add *` — добавление всех файлов в список отслеживаемых
3. `git commit -m "message"` — формирование коммита
4. `git push` — отправка изменений в свой форк

После этого на странице своего форка на GitHub нажимаем **Contribute → Open pull request**, проверяем diff и жмём зелёную кнопку **Create pull request**.

## Структура папок

```
reports/<Фамилия>/<Номер_лабораторной>/
    rep/    — отчёт (pdf/docx)
    src/    — ваш код (Python / Java / C++ / другой язык — на ваш выбор)
    tests/  — ваши тесты + tests/run_tests.sh (обязательный файл, см. ниже)
```

Пример:
```
reports/ivanov/lab1/rep/report.pdf
reports/ivanov/lab1/src/solution.py
reports/ivanov/lab1/tests/test_solution.py
reports/ivanov/lab1/tests/run_tests.sh
```

## `tests/run_tests.sh` — как писать тесты

Язык лабы вы выбираете сами (Python / Java / C++ / другой), поэтому единственное жёсткое требование — у каждой лабы в папке `tests/` должен лежать исполняемый скрипт **`run_tests.sh`**, который:

- запускается CI с рабочей директорией = папка лабы (то есть пути внутри пишете как `src/...`, `tests/...`);
- сам собирает (если нужно) и запускает ваши тесты;
- завершается кодом **0**, если все тесты прошли, и **любым другим кодом**, если хотя бы один тест упал.

Что тестировать и как — решаете сами: юнит-тесты на отдельные функции, тесты по спецификации, сравнение вывода программы с эталонным — всё, что доказывает работоспособность вашего решения.

Готовые шаблоны на выбор — скопируйте нужный в `tests/run_tests.sh` своей лабы и адаптируйте:
- [`examples/run_tests_templates/run_tests.python.sh`](examples/run_tests_templates/run_tests.python.sh) — pytest
- [`examples/run_tests_templates/run_tests.java.sh`](examples/run_tests_templates/run_tests.java.sh) — Maven/JUnit
- [`examples/run_tests_templates/run_tests.cpp.sh`](examples/run_tests_templates/run_tests.cpp.sh) — g++ без фреймворка

На раннере уже есть из коробки: Python 3, несколько версий JDK, Maven, Gradle, GCC/Clang, CMake, make — ничего доустанавливать не нужно, если вы укладываетесь в стандартный набор. Сеть на раннере тоже есть, так что `pip install` / `mvn` для доп. зависимостей внутри `run_tests.sh` работает, но замедляет прогон.

Таймаут на одну лабу — 5 минут (`TEST_TIMEOUT_SECONDS`).

## Что проверяется автоматически при Pull Request

При каждом PR, затрагивающем `reports/**`, запускаются **два независимых workflow**:

### 1. Запуск ваших тестов (`run-tests.yml`)
Для каждой изменённой лабы выполняется её `tests/run_tests.sh`. Результат (прошли/не прошли, вывод, время) публикуется в Job Summary PR'а. Если `tests/run_tests.sh` отсутствует — проверка красная (тесты обязательны).

### 2. Проверка на уникальность (`uniqueness-check.yml`)
Курс не предполагает единых функциональных тестов от преподавателя (студенты сами решают, что и как тестировать), поэтому дополнительно контролируется самостоятельность работы:
- текст отчёта (`rep/*.pdf`, `*.docx`, `*.txt`, `*.md`) сравнивается со всеми ранее загруженными отчётами по **той же лабораторной работе** у других студентов (TF-IDF + косинусная близость);
- файлы `src/*` дополнительно сравниваются **побайтово (по хэшу)** — ловит случаи, когда код скопирован целиком.

Результат — Job Summary PR'а:
  - **дубликат / сходство ≥ 90%** → проверка падает, PR нельзя мержить без ручного разбора;
  - **сходство 60–90%** → проверка проходит, но выводится предупреждение для проверяющего;
  - иначе — всё зелёное.
